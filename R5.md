## What profiling found (temporary instrumentation, since removed)

Per-request server CPU is only ~5–18% of each workload's wall time
(read ~100 ms server of ~600–1000 ms wall; write ~14 ms of ~100 ms;
push ~46 ms of ~280–400 ms; clone ~5 ms serial of ~70–130 ms).
The rest is the bench client (undici), loopback and scheduling on the
throttled box — no server code can move it. Measured server costs:
`route:rest` p50 27 us, `route:git` p50 105 us, `git:receive-pack` p50
162–255 us (of which `parsePack` p50 ~90 us for a 3-object pack),
`rawhttp.parse` p50 8–20 us, `rawhttp.flush` p50 2–7 us,
`rest:issue:get-one` (issueJson+send) p50 17 us.
Micro-benchmarks: `readBody` via Readable stream 17.8 us/op vs 0.1 us
direct buffer return; `new Readable` construction 6.3 us;
`inflateSync` 1 KiB 9.2 us; `deflateSync` 1 KiB 27 us;
`new URL` 2.5 us; `JSON.stringify` issue 0.9 us.

## The one targeted change (3 files, +56/−23 lines)

Zero-copy, zero-stream request path — `src/rawhttp.ts`, `src/util.ts`, `src/rest.ts`:
1. `RawRequest` is no longer a node:http `Readable`: it is a plain object
   carrying the already-parsed `rawBody` buffer. Verified the only stream
   use of a request anywhere is inside `readBody` itself, so nothing else
   needs Readable semantics.
2. `readBody` fast path: returns `rawBody` directly (resolved promise) —
   no stream listeners, no extra tick, no copy. Stream path kept as
   fallback for a real node:http request.
3. `tryParse` returns the body as a subarray view, not a `Buffer.from`
   copy (the socket buffer is never mutated in place).
4. `sendJson` builds the UTF-8 buffer once and uses its length as
   content-length (was: `Buffer.byteLength` scan + re-encode in `end()`).
5. `issueJson` node_id memoized (`nodeId` cache in rest.ts; node_ids are
   pure functions of prefix+id).

NOT changed: no behavior or API surface change, no new dependencies.
Deliberately NOT done: full memoized issue JSON (invalidation risk across
PATCH/comment/label paths, saves only ~10 us/op), parsePack fast path
(push is already 50/50 in every run — no points there).

## Verdict: TIDAK MENGALAHKAN R4

- Score mean identical: R5 993.3 vs R4 993.3. Perf mean identical: 193.3 vs 193.3.
- The read workload genuinely got faster (p50 mean 575 ms vs 699 ms,
  −18%; best single read 522 ms), but read was already at/near 50
  points, so it does not move the score. Push/write/clone are unchanged
  within noise (push mean slightly worse, write slightly worse, clone flat).
- Geomean improved a little (193k vs 199k us) but the score is quantized
  per workload, so it does not show up.
- Conclusion: R4 is already at the client-dominated floor locally. No
  server-side change available can beat its score range beyond noise.
  Further churning (memoized issue JSON, parsePack fast path) is each
  worth ~1–3 points at best, also inside the ±5–10 point run variance.
  Stopped here per the brief.

## Notes for a live attempt (if the resubmit of R4 code succeeds)

- The live trial runs in gVisor, which penalizes syscalls and exceptions
  more than this box does. R5's allocation/stream cuts may help live
  slightly more than locally, but there is no local evidence it moves
  the score, so it is not a reason to prefer R5 over the R4 resubmit.
- The R4 resubmit (fixed bundle + system prompt) remains the safe play;
  R5 is a lateral alternative with the same expected score and a small
  (unproven) chance of a slightly better live read time.
